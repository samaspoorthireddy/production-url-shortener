# SS-104: Stripe Sandbox Payments Webhook Spike [AI-Ready]

## 1. Title
SS-104: Stripe Sandbox Payments Webhook Spike

## 2. Context (Why)
We need a standalone sandbox route to verify Stripe Hosted Checkout redirection and webhook signature validation in test mode. This retires payment integration risks early and addresses investor demo pressure.

## 3. Scope (What)
- Create a new router module at `app/routers/payments.py` and mount it in `main.py`.
- Implement `POST /api/payments/session` to create a hardcoded $50 Stripe Checkout Session.
- Implement `POST /api/payments/webhook` to process Stripe webhook notifications.

## 4. Interface Contract (Inputs/Outputs/Data Shapes)
- **POST /api/payments/session**:
  - Request Body: `{}` (No inputs required)
  - Success Response (200 OK):
    ```json
    { "checkout_url": "string (valid Stripe checkout URL)" }
    ```
- **POST /api/payments/webhook**:
  - Headers:
    - `Stripe-Signature`: "string"
  - Request Body: Raw binary bytes (Stripe event payload)
  - Success Response (200 OK):
    ```json
    { "status": "received" }
    ```
  - Error Response (400 Bad Request):
    - Triggers if signature verification fails.

## 5. Acceptance Criteria (Testable Conditions)
- **Given** Stripe test credentials in the environment, **when** a POST is made to `/api/payments/session`, **then** return status code 200 and a Stripe URL configured for a single unit purchase of "SkillSwap Session" valued at $50.00 USD.
- **Given** a valid raw request signature matching the local webhook secret, **when** a POST containing a `checkout.session.completed` event is received at `/api/payments/webhook`, **then** extract the session ID, log the payment details in structured JSON console logs, and return status code 200.
- **Given** an invalid Stripe signature header, **when** a webhook request is received, **then** return status code 400 Bad Request.
- **Given** a request payload exceeding 1MB is sent to the webhook endpoint, **when** the endpoint runs, **then** it rejects the request with status code 413 Payload Too Large.
- **Given** a Stripe webhook event that has already been processed (duplicate delivery), **when** it is received, **then** return 200 OK without double-processing (log as duplicate).

## 6. Constraints (Rules to Follow)
- **Route Definition:** Route handler must reside in a new file `app/routers/payments.py`.
- **Registration:** Mount the new router in `main.py` using `app.include_router`.
- **Library:** Use the `stripe` python SDK library for session creation and signature verification.
- **Stripe Credentials:** Read Stripe keys from standard environment variables:
  - `STRIPE_SECRET_KEY` (Stripe private key)
  - `STRIPE_WEBHOOK_SECRET` (Webhook signature verifier secret)
- **Signature Verification:** The webhook endpoint must verify the raw request body against the `Stripe-Signature` header using `stripe.Webhook.construct_event`. Return 400 Bad Request if signature verification fails.
- **Payload Size Restriction:** Validate and limit the raw request body size to a maximum of 1MB before parsing to prevent Denial of Service (DoS) attacks. Return 413 Payload Too Large on breach.
- **Webhook Idempotency:** Track processed Stripe Event IDs (in-memory list is acceptable for this spike). If an event ID is already present, log a WARNING: `Duplicate Stripe webhook event received: event_id={event_id}` and return 200 OK without running business actions.
- **Error Handling:** Uncaught exception handling must conform to the global exception handler. Webhook signature parsing exceptions must return 400 Bad Request, whereas Stripe API timeouts must return 503 Service Unavailable (with no tracebacks leaked).
- **Logging:** Use structured console logging. Log checkout session creation at INFO: `Created Stripe Checkout Session: session_id={session_id}`. Log webhook event reception at INFO: `Stripe webhook received: event_id={event_id}, type={event_type}`. Log successful payment processing at INFO: `Stripe payment processed successfully: session_id={session_id}`.

## 7. Anti-Scope (What NOT to Build)
- No database model updates or transactional history persistence.
- No client/user authentication constraints.
- No refund, invoice receipt creation, or dispute handling logic.
