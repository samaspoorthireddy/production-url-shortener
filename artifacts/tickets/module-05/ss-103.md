# SS-103: GET /api/providers/:id - View Provider Profile Details

## 1. Title
SS-103: GET /api/providers/:id - View Provider Profile Details

## 2. Context (Why)
We need an API endpoint to allow clients to retrieve the public profile details of an approved service provider.

## 3. Scope (What)
- Implement a `GET /api/providers/{provider_id}` route inside `app/routers/providers.py`.
- Enforce public profile access restrictions (only approved providers can be viewed by the public; unapproved/pending listings must return a forbidden error).

## 4. Interface Contract (Inputs/Outputs/Data Shapes)
- **Path Parameter**:
  - `provider_id`: String (UUID format)
- **Success Response (200 OK)**:
  - Same JSON structure as the success response in `SS-102` (contains provider details + embedded services list).
- **Error Responses**:
  - **400 Bad Request** (Malformed path parameter):
    ```json
    { "detail": "Invalid provider ID format" }
    ```
    - Triggers if `provider_id` is not a valid UUID format.
  - **404 Not Found** (Not found or not approved):
    ```json
    { "detail": "Provider not found" }
    ```
    - Triggers if no provider record matches the requested UUID, or if the provider exists but is not in `'approved'` status (this prevents provider enumeration scanning and data leakage of pending listings).

## 5. Acceptance Criteria (Testable Conditions)
- **Given** an approved provider exists in the database, **when** a client makes a `GET /api/providers/{provider_id}` request, **then** it returns status code 200 and the matching profile payload.
- **Given** a provider exists in the database with status `pending_approval` or `rejected`, **when** a client makes a `GET /api/providers/{provider_id}` request, **then** it returns status code 404 Not Found.
- **Given** a provider ID does not exist in the database, **when** a client makes a `GET /api/providers/{provider_id}` request, **then** it returns status code 404 Not Found.
- **Given** a client sends an invalid UUID string as a `provider_id`, **when** the endpoint runs, **then** it returns status code 400 Bad Request.

## 6. Constraints (Rules to Follow)
- **Route Injection:** Route handler must be added to the existing `app/routers/providers.py`.
- **Schemas:** Re-use the response schemas defined in `app/schemas/provider.py`.
- **Dependency Injection:** Inject the DB session dependency using the existing `get_db` from `database.py`.
- **Path Parameter Validation:** Explicitly validate that `provider_id` conforms to a standard UUID version 4 format (e.g., using Pydantic or a regex pattern in the path parameter type check). Return 400 Bad Request on failure.
- **Enumeration Attack Prevention:** Do not return 403 Forbidden for pending/rejected listings. Always return 404 Not Found to prevent malicious clients from mapping our database.
- **Authentication:** None required for public directory lookup.
- **Error Handling:** Conforms to the application's global exception handler. Uncaught database or JSON parsing errors must return a standard obfuscated 500 error.
- **Logging:** Log successful profile lookups at INFO level: `Profile fetched: provider_id={provider_id}`. Log missing or malformed lookups at WARNING level: `Profile fetch failed for provider_id={provider_id}, status={status_code}`.

## 7. Anti-Scope (What NOT to Build)
- No user authentication or session checks (anonymous users can view approved profiles).
- No query parameters, searching, filtering, or list directory routes (separate ticket).
